### 题目1：String 内存指向
> String s1 = "java"; 和 String s2 = new String("java");，== 和 equals 的结果？

**我的初答**：==的结果是true,equals不懂
<details>
<summary><strong>点击展开标准解析</strong></summary>

- **`s1 == s2` 为 `false`**：`s1` 指向**字符串常量池**（String Pool）中的地址；`s2` 指向**堆内存**（Heap）中新创建的对象地址。两者内存地址不同。
- **`s1.equals(s2)` 为 `true`**：`String` 类重写了 `equals()`，逐个比较底层 `char[]` 数组的字符序列是否相同。
- **进阶加分项**：如果想让 `s2 == s1` 返回 `true`，可以调用 `s2.intern()`，该方法会强制将堆中的字符串引用指向常量池中已有的对象。
</details>

### 题目2：ArrayList vs LinkedList
> 分别适合什么场景？

**我的初答**：不知道
<details>
<summary><strong>点击展开标准解析</strong></summary>

- **`ArrayList`（底层数组）**：**查询修改快**（O(1) 随机访问），**中间插入/删除慢**（需 `System.arraycopy` 移动元素）。适合**读多写少**的场景（实际项目占比超 95%）。
- **`LinkedList`（底层双向链表）**：**头部/尾部插入删除快**（O(1) 改指针），**查询慢**（O(n) 需从头遍历）。适合**头部频繁插入**的场景（如队列）。
- **致命误区**：很多人误以为 `LinkedList` 所有增删都快，但在**中间位置增删**时，两者都需先遍历到该位置，`ArrayList` 遍历更快，所以反而胜出。
- **加分项**：提及 `ArrayList` 扩容机制为 **1.5 倍**（JDK 8），建议开发中预估容量，使用 `new ArrayList<>(initialCapacity)` 避免频繁扩容。
</details>
**错漏点**：需要学习ArrayList和LinkedList的相关知识

### 题目3：HashMap 哈希寻址
> 如何确定下标？哈希冲突怎么办？
<details>
<summary><strong>点击展开标准解析</strong></summary>

**执行流程分三步**：

1.  **算哈希（扰动）**：调用 `key.hashCode()` 得到原始哈希，再执行 `h ^ (h >>> 16)`（高16位与低16位异或）。目的是让高位特征参与低位运算，**减少哈希碰撞**。
2.  **算下标（寻址）**：使用 `(n - 1) & hash` 计算数组下标（`n` 为数组长度，必须是 2 的幂）。此处用位运算代替取模 `%`，**效率更高**。
3.  **冲突解决（拉链法）**：若下标相同，先比较 `==` 地址，再比较 `equals()` 内容。若 key 完全相等则覆盖旧值；否则以**链表**形式挂载（JDK 8 尾部插入）。

- **进阶升级（树化）**：当链表长度 **> 8** 且数组长度 **≥ 64** 时，链表转为**红黑树**（O(log n)）。若数组长度 < 64，优先扩容而非树化，防止因数组过小导致的哈希碰撞。
</details>

**我的初答**：
1. 通过计算要加入的元素的哈希值来确定下标
2. 出现哈希冲突会先遍历对应下标的链表/红黑树,通过equals方法判断内部属性的Key和是否相同,如果Key相同,则覆盖Value

**错漏点**：
1. 通过HashMap内部扰动后的哈希值对数组长度进行等价取模计算下标(不是hashCode()获得的原始哈希值)
2. 两个Key经过扰动函数得到扰动后的hash值h再进行 h & (table.length-1)计算得到相同下标,这就是HashMap定义的哈希冲突
3. 先会遍历比较链表/红黑树的每个元素的Key的扰动后的hash值.相同再equals比较内部属性值,如果遍历完吗,没有相同hash,就挂载再链表后或者经过红黑规则检验后放入红黑树
#### 扰动函数真正的目标: 原生hashCode往往高位变化频繁,低位变化小,而寻址只看低位.扰动函数会把高位信息混合到低位,让低位更均匀,最终目标是减少下标冲突(桶碰撞),而不是减少原生hashCode本身冲突
#### 为什么数组过小会导致哈希碰撞? 数组长度n 掩码mask = n-1,mask二进制有多少个1,就代表寻址会取用hash值末尾多少位.数组长度小,映射空间缩小,碰撞概率自然上升

### 题目1：重载（Overload）与重写（Override）的区别
> 请简述两者的区别，并说明它们在编译期和运行期的表现差异？

<details>
<summary><strong>点击展开标准解析</strong></summary>

- **重载（Overload）**：**同一类中**，方法名相同，**参数列表不同**（类型、个数、顺序）。与返回值无关。属于**编译期多态**（静态绑定），编译时根据传入参数决定调哪个。
- **重写（Override）**：**子类继承父类**，方法名、参数、返回值完全相同，访问修饰符不能更严格。属于**运行期多态**（动态绑定），运行时根据对象实际类型决定调哪个。
- **高频追问**：构造器能重写吗？**不能**（构造器不能被继承）。
</details>

**我的初答**：重载Overload是同一类下的相同方法,但参数列表不同 重写Override不了解
**错漏点**：Overload与返回值无关

### 题目2：equals() 与 hashCode() 的契约
> 为什么重写 `equals()` 时必须重写 `hashCode()`？只重写 equals 在 HashMap 中会出什么 Bug？

<details>
<summary><strong>点击展开标准解析</strong></summary>

- **核心契约**：两个对象如果 `equals()` 返回 `true`，则 `hashCode()` **必须相等**。如果 `equals` 返回 `false`，`hashCode` 可以相等（允许冲突）也可以不等（提高性能）。
- **只重写 equals 的 Bug**：假设自定义 `Student` 类，`id` 相同视为同一人。只重写 `equals` 不重写 `hashCode`，放入 `HashMap` 作为 key 时，`put` 会先算 `hashCode` 定位桶，再 `equals` 找值。两个相同 `id` 的对象 `hashCode` 不同，会被**放到不同桶里**，导致 `map.get(student1)` 拿不到 `student2` 存进去的值，**逻辑上相等的对象在集合中变成了两个键**，造成内存泄漏和业务错误。
- **加分项**：`HashSet` 底层就是 `HashMap`，同样会中招。
</details>

### 题目1：final、finally、finalize 的区别
> 这三个关键字/机制分别是什么？各自的使用场景？

<details>
<summary><strong>点击展开标准解析</strong></summary>

- **final（关键字）**：
    - 修饰**类**：不可被继承（如 `String`）
    - 修饰**方法**：不可被子类重写
    - 修饰**变量**：基本类型值不可变，引用类型不可指向新对象（但对象内容可变）
- **finally（代码块）**：
    - 与 `try-catch` 配合，**无论是否发生异常，都会执行**（除非 JVM 提前退出）
    - 通常用于释放资源（关闭文件流、数据库连接等）
- **finalize（方法）**：
    - `Object` 类的方法，GC 回收对象前会调用（已废弃，JDK 9 标记为弃用）
    - **不推荐使用**：调用时机不确定，执行不可靠，容易引起性能问题
- **一句话总结**：final 是“不变”，finally 是“必须执行”，finalize 是“临终遗言（已过时）”。
</details>

### 题目3：检查型异常（Checked）与非检查型异常（Unchecked）的区别
> Java 中异常分为哪两大类？`RuntimeException` 属于哪一类？分别举例说明。

<details>
<summary><strong>点击展开标准解析</strong></summary>

- **检查型异常（Checked Exception）**：
    - 继承自 `Exception` 但**不继承** `RuntimeException`
    - 编译器**强制要求**处理（`try-catch` 或 `throws`）
    - **典型例子**：`IOException`、`SQLException`、`ClassNotFoundException`
- **非检查型异常（Unchecked Exception）**：
    - 继承自 `RuntimeException`
    - 编译器**不强制**处理，运行时才会抛出
    - **典型例子**：`NullPointerException`、`ArrayIndexOutOfBoundsException`、`ArithmeticException`、`ClassCastException`
- **设计理念**：Checked 代表可恢复的异常（如文件不存在），调用者应妥善处理；Unchecked 代表编程错误（如空指针），应在代码层面避免。
- **高频追问**：Spring 事务管理中，默认 **只对 Unchecked 异常回滚**，Checked 异常不会触发回滚。
</details>

> 为什么 `main` 方法必须是 `static` 的？在 `static` 方法中能否使用 `this` 关键字？能否直接调用非静态方法？为什么？

- **一句话总结**：静态成员属于类，实例成员属于对象。静态环境中没有对象，所以不能碰任何和对象相关的成员。
</details>

### 题目3：HashMap 扩容机制（JDK 1.8）

  3. **红黑树拆分**：如果桶上已是红黑树，扩容时会拆分为两个子树（低位和高位），分别挂到新数组的相应位置。
- **加分项**：如果放入的 key 已实现 `Comparable`，红黑树维护时还会利用比较顺序提升效率。

### 题目3：JVM 中垃圾回收的“分代理论”与三种基本算法
> 为什么 JVM 要把堆内存划分为新生代和老年代？分别对应哪三种垃圾回收算法？各自适用于哪一代？

<details>
<summary><strong>点击展开标准解析</strong></summary>

- 分代理论依据（弱分代假说）：绝大多数对象都是朝生夕灭，熬过多次 GC 的对象则长期存活。分代管理可提升回收效率，避免全堆扫描。
- 三种基本算法：
  1. 标记-清除（Mark-Sweep）：标记存活对象，清除未标记对象。缺点：产生内存碎片，导致大对象无法分配。适合老年代（CMS 使用）。
  2. 标记-整理（Mark-Compact）：标记存活对象后，将所有存活对象移动到连续内存区域，清除边界外空间。优点：无碎片。适合老年代（Serial Old 使用）。

- 现代 JVM 实践：新生代用**复制算法**（如 Parallel Scavenge、G1 的年轻代回收），老年代用**标记-整理**或**标记-清除**（如 CMS 用标记-清除，G1 用标记-整理）。

- ThreadLocal 内部 Entry 的 key（即 ThreadLocal 本身）是**弱引用**（WeakReference），value 是强引用。

  1. 每次使用完后，在 finally 中调用 `remove()` 方法，显式清除 Entry。

### 题目3：ConcurrentHashMap 的底层实现与锁粒度

<summary><strong>点击展开标准解析</strong></summary>

### 题目2：CAS 原理及其 ABA 问题
> CAS（Compare-And-Swap）是什么？它有哪些缺点？什么是 ABA 问题？如何解决？

<details>
<summary><strong>点击展开标准解析</strong></summary>

- CAS 原理：一种**乐观锁**技术，底层依赖 CPU 的 CMPXCHG 指令。它包含三个操作数：内存值 V、预期值 A、更新值 B。仅当 V == A 时，才将 B 赋值给 V，否则自旋重试（循环）。
- 三大缺点：
  1. **自旋开销大**：长时间循环不成功会消耗大量 CPU 资源。
  2. **只能保证单个变量的原子操作**：多个变量需要配合锁或合并为对象（如 AtomicReference）。
  3. **ABA 问题**：内存值从 A → B → A，CAS 检查时认为值未变，但实际上已发生变化。
- ABA 解决方法：使用 **AtomicStampedReference**（带版本号/时间戳）或 **AtomicMarkableReference**，每次修改不仅更新值，还更新版本号，比较时同时检查值和版本号。
- 典型案例：Java 中的 `AtomicInteger` 使用 CAS 实现自增，`AtomicStampedReference` 用于解决 ABA 场景。
</details>

### 题目3：BIO、NIO、AIO 的区别与适用场景
> 简述 Java 中 BIO、NIO、AIO 三种 IO 模型的核心区别（同步/阻塞、适用场景）。为什么 Netty 底层是基于 NIO 而非 AIO？

<details>
<summary><strong>点击展开标准解析</strong></summary>

- **BIO（同步阻塞 I/O）**：
  - 模型：一个连接对应一个线程，read/write 操作会阻塞线程直到数据就绪或完成。
  - 适用场景：**连接数少、并发不高的传统应用**（如简单的 CRUD 后台），代码简单易维护。
- **NIO（同步非阻塞 I/O）**：
  - 模型：基于 **Selector（多路复用器）** + Channel + Buffer，一个线程可以监听多个 Channel 的事件（连接、读写），通过轮询机制实现非阻塞。
  - 适用场景：**高并发、连接多但数据量小的场景**（如即时通讯、游戏服务器）。Netty 默认基于 NIO，因为其性能优异且生态成熟。
- **AIO（异步非阻塞 I/O）**：
  - 模型：真正的异步 I/O，读写操作提交后立即返回，由操作系统内核完成数据拷贝后主动通知回调函数（CompletionHandler）。
  - 适用场景：**连接数极多且每个连接耗时较长**（如大文件传输），但当前底层实现（Windows 的 IOCP / Linux 的 epoll 模拟）在 Linux 上性能并不比 NIO 有明显优势，且编程复杂，所以 Netty 等主流框架未采用。
- 发展顺序：**BIO → NIO → AIO**，目前企业级开发中 NIO 是绝对主流。
</details>

### 题目3：CopyOnWriteArrayList 的设计原理与适用场景

  1. 写操作成本高（每次都要复制整个数组），频繁写会引发性能瓶颈和内存开销。
  2. 数据**不保证实时一致性**（读操作可能读到旧数据，因为写操作还在进行中）。
- 适用场景：**读操作远多于写操作**，且对数据实时性要求不高（如黑白名单缓存、配置列表）。

- **REQUIRES_NEW**：**挂起当前事务**，新建一个独立事务。A 和 B 属于**不同事务**。B 抛异常仅回滚 B，A 不受影响（除非 A 捕获异常后手动回滚）。

- **关键结论**：REQUIRED 是整体回滚；REQUIRES_NEW 是各自独立回滚；NESTED 是子事务回滚不影响父事务，但父事务回滚会牵连子事务。

<summary><strong>点击展开标准解析</strong></summary>

### 题目2：fail-fast 与 fail-safe 迭代器的底层实现区别（modCount vs 快照）

<summary><strong>点击展开标准解析</strong></summary>

> 在实际 SQL 开发中，哪些写法会导致索引失效？请列举至少 5 种常见场景，并简要说明如何通过 Explain 执行计划判断索引是否被正确使用（如 type、key、Extra 字段的解读）。

<details>
<summary><strong>点击展开标准解析</strong></summary>

- 常见索引失效场景：
    1. 对索引列使用函数或表达式（如 `WHERE DATE(create_time) = '2025-01-01'` → 应改为范围查询 `create_time BETWEEN ...`）。
    2. 隐式类型转换（如 `WHERE phone = 13800138000`，phone 是 varchar 类型，传入数字时不会走索引）。
    3. 使用 LIKE 且以通配符开头（如 `WHERE name LIKE '%张三'` → 前缀模糊会导致全表扫描）。
    4. OR 条件中有非索引列（如 `WHERE age = 20 OR name = '张三'`，若 name 无索引则索引失效）。
    5. 范围查询后紧跟其他索引列（如 `WHERE age > 20 AND name = '张三'`，在联合索引 (age, name) 中，age 范围查询会使 name 列的索引失效，即最左匹配原则中断）。

    - type：连接类型，效率从高到低依次为 system > const > eq_ref > ref > range > index > ALL（至少达到 range 级别）。
    - possible_keys：可能使用的索引，key：实际使用的索引。
    - Extra：Using index（覆盖索引，无需回表，最优）、Using where（需回表过滤）、Using filesort（文件排序，需优化）、Using temporary（临时表，需优化）。
- 优化策略：针对失效场景改写 SQL，或创建合适的联合索引，并定期通过慢查询日志分析执行计划。

### 题目3：分布式事务框架 Seata 的 AT 模式原理（一阶段 + 二阶段）
> Seata 的 AT 模式如何实现自动补偿？请简述一阶段（执行 SQL + 前置镜像/后置镜像）和二阶段（提交或回滚）的底层机制。为什么说它是“自动”补偿，而 TCC 是“手动”补偿？

<details>
<summary><strong>点击展开标准解析</strong></summary>

- AT 模式核心原理（基于数据库本地事务 + 拦截 SQL）：
    - 一阶段（执行 SQL）：
        1. 代理数据源，拦截业务 SQL，解析为 SQL 类型（Insert/Update/Delete）。
        2. 执行 SQL 前，查询数据的前置镜像（before image），记录原始数据（通过 Select 语句）。
        3. 执行业务 SQL，修改数据库。
        4. 执行 SQL 后，查询数据的后置镜像（after image），记录修改后的数据。
        5. 将前置镜像和后置镜像及 SQL 元数据写入 Undo Log（回滚日志表）。
        6. 提交本地事务（此时数据已落库，并持有全局锁）。
    - 二阶段（提交或回滚）：
        - 提交（commit）：TC 发送提交指令，各 RM 异步删除 Undo Log，释放全局锁（最终完成）。
        - 回滚（rollback）：TC 发送回滚指令，各 RM 根据 Undo Log 中的前后镜像生成逆向 SQL（如 Update 还原为 before image），执行回滚，清除 Undo Log。
- 为什么是“自动”补偿：开发者只需写业务 SQL，Seata 自动完成 undo 日志记录和逆向 SQL 生成，无需手动写 TCC 的三个接口（Try/Confirm/Cancel）。
- 限制：要求数据库支持 ACID 本地事务（如 MySQL InnoDB），且 SQL 必须是确定性的（不能有随机函数）。
</details>
